## 接入前的二轮审计：新增 4 个阻断性问题（读代码时发现）

1. **`ThreadSafeReranker.predict()` 的「降级」是假的** —— `concurrent_singleton.py:194-195` 日志写 "falling back to original scores"，实际 `return [0.0] * len(pairs)`。**返回全 0 分而非原始分**，一旦直连主链路会把精排顺序彻底打乱。接入时必须改成返回 `None`/抛异常，由调用方回退。
2. **生产 `Reranker._ensure_model_loaded()` 非线程安全** —— `reranker.py:47-87`：先无条件置 `self._model_loaded = True`，且 `_model_cache` / `_model_load_attempted` 两个模块级全局无锁。并发首次请求时，后到线程会命中 `_model_load_attempted` 直接 `return False` → **静默降级为不精排**。单例只保证了「实例唯一」，没保证「加载唯一」。
3. **`ConnectionPool.stats` 没有 `active` 字段** —— `metrics.py:253/256` 读 `pool_stats.get("active", 0)`，恒为 0；且 `pool_size` 是「空闲数」不是「池容量」，指标语义本身也是错的。
4. **硬编码 Milvus 地址** —— `concurrent_singleton.py:376-377` `host="192.168.86.132", port="19530"` 写死，未走 `settings`。接池之前必须先参数化。

另：`_set_cache` 淘汰用 `min(时间戳)` = FIFO（非 LRU）；`ConnectionPool` 无重连重试（「自动重连」名不副实）；两套 `SingletonManager` 同名不同模块，是后续维护的踩坑源。

5. **B10 的问题机理** —— `async def` 内调同步 `threading.Semaphore.acquire(timeout=30)` 冻结的是**整个事件循环**（非当前请求），最坏 30s 全站停摆；`model.predict` 同理由（CPU 密集）。改 `asyncio.Semaphore` + `asyncio.wait_for` + `asyncio.to_thread`。

## 补测一：嵌入服务「假死」事件（Q1）

**结论订正：服务从未宕机也从未重启（`RestartCount=0`），是自行排空积压后恢复的。**

**九步排查法（可复用）：**
1. TCP 层探测 → 端口通 = 进程活着（排除宕机）
2. 轻量端点 `/health` `/v1/models` `/docs` → 全 200 = 框架层健康（排除服务整体故障）
3. 拉长超时重测 → 1.4s 返回 = 已自愈（排除死锁）
4. `docker inspect` → `RestartCount=0` + CPU 0.14% = 自愈且是「阻塞」非「过载」
5. 读日志 → 只记 52 条请求 + 存在「客户端超时但服务端回 200」= 幽灵请求积压
6. **读服务端源码 → 根因**：`async def embeddings` 里同步调用 `model.encode()`
7. **容器内探针验证** → 重负载期间 `/health` 连续 5s 超时 = 确证事件循环阻塞
8. 容量标定 → 0.4 条/秒，批量 1→32 无收益（算力受限）
9. 还原事故链 → 客户端 30s 超时 vs 服务端 50–250s 实际耗时

## 补测三：自我更正 —— 阻塞 ≠ CPU 耗尽

**起因：** 用户问「阻塞事件循环是不是导致 CPU 资源耗尽」。答案是否，
并暴露出**我前面一条推理用错了证据**。

**错的推理：** 事故报告第 4 步写「CPU 只有 0.14% ⇒ 不是在忙着算，是卡住不动」。
**但那个采样点是在积压已经排空之后取的**，描述的是恢复后的状态，不是阻塞期间的状态。
`docker stats` 是瞬时快照，不能这么用。

**精细重测（边压边测，16 条 × 255 字，请求总耗时 41.4s）：**

```
容器内 nproc = 2    torch.get_num_threads() = 2     （CPU 上限 = 200%）
采样 1~3 : CPU 114% / 112% / 121%   /health = 000 超时
采样 4   : CPU 109.65%              /health = 200 (5ms)   ← CPU 一样忙，响应却恢复了
采样 5~10: CPU 0.11~0.27%           /health = 200 (~2ms)
```

**两条结论：**
1. **CPU 没被耗尽**：峰值 110–121%（2 核上限 200%），约 0.8 个核空闲。
2. **响应能力与 CPU 忙闲无关**：采样 4 上 CPU 仍是 109.65% 而 `/health` 已恢复
   ⇒ 瓶颈是「事件循环那个单一线程是否可用」，不是「CPU 还剩多少」。

**概念区分（关键）：**
- 阻塞事件循环 = **并发能力**问题 → 改代码
- CPU 耗尽 = **资源容量**问题 → 加硬件 / 换模型
- 两者**独立**：只修前者吞吐仍是 0.4 条/秒；只修后者高负载下照样整体假死

**顺带纠正一个常见误解：** 「同步调用释放 GIL 所以事件循环还能跑」是错的。
GIL 释放的是「其他操作系统线程」，而事件循环是**某一个特定线程**，它正卡在同步调用里。
真正起作用的是**换了执行线程**（`run_in_threadpool`）。

**已同步修正：**
- `docs/EMBEDDING_SERVICE_INCIDENT.md` —— 第 4 步加更正说明；新增
  「第 7 步之二：阻塞期间 CPU 到底占了多少」整节；修正根因表与 5.2 节的 GIL 表述
- 技能 `service-hang-diagnosis` —— **删掉错误启发式**「CPU 极低 ⇒ 是阻塞」，
  改为「第 4 步之二：阻塞 ≠ CPU 耗尽」+ 正确测法 + GIL 误解
