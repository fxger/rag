## 接入前的二轮审计：新增 4 个阻断性问题（读代码时发现）

1. **`ThreadSafeReranker.predict()` 的「降级」是假的** —— `concurrent_singleton.py:194-195` 日志写 "falling back to original scores"，实际 `return [0.0] * len(pairs)`。**返回全 0 分而非原始分**，一旦直连主链路会把精排顺序彻底打乱。接入时必须改成返回 `None`/抛异常，由调用方回退。
2. **生产 `Reranker._ensure_model_loaded()` 非线程安全** —— `reranker.py:47-87`：先无条件置 `self._model_loaded = True`，且 `_model_cache` / `_model_load_attempted` 两个模块级全局无锁。并发首次请求时，后到线程会命中 `_model_load_attempted` 直接 `return False` → **静默降级为不精排**。单例只保证了「实例唯一」，没保证「加载唯一」。
3. **`ConnectionPool.stats` 没有 `active` 字段** —— `metrics.py:253/256` 读 `pool_stats.get("active", 0)`，恒为 0；且 `pool_size` 是「空闲数」不是「池容量」，指标语义本身也是错的。
4. **硬编码 Milvus 地址** —— `concurrent_singleton.py:376-377` `host="192.168.86.132", port="19530"` 写死，未走 `settings`。接池之前必须先参数化。

另：`_set_cache` 淘汰用 `min(时间戳)` = FIFO（非 LRU）；`ConnectionPool` 无重连重试（「自动重连」名不副实）；两套 `SingletonManager` 同名不同模块，是后续维护的踩坑源。

1. **`CircuitBreaker` 根本不是中间件** —— `src/api/middleware/circuit_breaker.py` 中是**纯状态机**（方法只有 `__init__/state/_on_success/_on_failure/async call/stats/reset`，**不继承 `BaseHTTPMiddleware`、无 `dispatch`**）。清单 A2 原写「`app.add_middleware(CircuitBreakerMiddleware, ...)`」**行不通，该类不存在**。正确做法是**在调用点用 `await breaker.call(fn, ...)` 包裹**（保护下游依赖，而非熔断整个 API）。
2. **B5 实为 3 处协调改动**，不是「改一行」：`retrieve()` 返回 `RetrievalResult`（有 `.results`），而 `build_with_sources()` 期望 `list[SearchResult]`；异常分支又把 `results` 置为 `[]`（类型漂移）→ 即使改对 `len()`，第 103 行仍崩。须统一为 `list[SearchResult]`，这正是「结果恒空」的完整机制。
3. **B4 需新建 `src/core/tokenization.py`** 作为 token 口径的**单一事实来源**（`estimate_tokens` / `split_tokens` / `token_spans`），chunker 与 context_builder 共用。`_truncate_to_tokens` 改用**二分查找字符前缀**（原 `max_chars = max_tokens * 4` 中文错 4 倍）。
4. **B1 修复后遗留口径分裂** —— 英文 3060 字符 1 块但上报 `token_count=764 > 512`：分块按 token 个数、上报按字符启发式。**与 B4 同根，须在 B4 一并解决**。
5. **B10 的问题机理** —— `async def` 内调同步 `threading.Semaphore.acquire(timeout=30)` 冻结的是**整个事件循环**（非当前请求），最坏 30s 全站停摆；`model.predict` 同理由（CPU 密集）。改 `asyncio.Semaphore` + `asyncio.wait_for` + `asyncio.to_thread`。
6. **中间件顺序 LIFO 陷阱** —— Starlette `add_middleware` 后添加的先执行，要得到「CORS → 限流 → 熔断 → Metrics」的执行序，代码里必须**反向书写**。
7. **A2 的替代路线评价** —— 建议走「调用点包装」而非新写 `BaseHTTPMiddleware`（后者会因下游抖动熔断整个 API，粒度过粗）。

## 七轮：A4（QueryRewriter / HyDE）决策落定 —— 不接入

**用户决策：** A4 采用「代码留着当可选扩展」方案 = **不接入主链路，代码原样保留，简历不提**。

**决策依据（四笔账）：**

| 维度 | 事实 | 结论 |
|---|---|---|
| 延迟 | 检索仅 **15.1ms**，LLM 生成为秒级；`rewrite()`/`hyde()` 各插入 1 次 LLM 前置调用（+1~3s） | 优化链路最短一段，总延迟反增 50%~100% |
| 成本 | `rewrite()` `max_tokens=500`、`hyde()` `max_tokens=600` 各带完整提示词；每次查询 LLM 调用 1 次 → 2~3 次 | DeepSeek 按量计费，账单翻倍以上 |
| 收益 | 混合检索 BM25 侧（jieba 分词）本身按词匹配，已覆盖大部分词汇鸿沟 | 边际收益被削弱 |
| 举证 | 无 C3 对照实验 | 面试追问「提升多少」答不出，加分变减分 |

**概念澄清（本轮为用户讲解，可复用）：**
- 两者共同解决**词汇鸿沟**（vocabulary mismatch）→ 目标是**提升召回**，且都是**零样本**方案（无需标注数据/重训模型）
- **多查询扩展**：横向 —— LLM 把 1 个查询改写成 N 种问法（默认 3），各检索一次后 RRF 融合，原始查询保留在首位。靠**覆盖面**取胜
- **HyDE**（Gao et al. 2022, *Precise Zero-Shot Dense Retrieval without Relevance Labels*）：纵向 —— LLM 针对问题**编一段理想答案**，用**假答案**的向量去检索。关键洞察：**假答案不必正确，只要「像文档」**（向量匹配措辞风格分布而非事实真伪）；仅对**稠密向量检索**有效，对 BM25 无意义
- 共同代价：额外 1 次 LLM 调用、可能引入噪声（错误变体拉低精度）、必须实测收益
