# 嵌入服务「假死」事件排查报告

> 日期：2026-09-14
> 对象：VM1 `192.168.86.132`，容器 `qwen-embeddings-2.0-small`
> 触发场景：C4 容量测试的批量灌库
> 复现脚本：`scripts/embedding_service_probe.py`

---

## 摘要（一句话）

**服务从未宕机，也从未被重启。** 它被一批在 2 核 CPU 上根本算不完的嵌入请求灌满，
而它的 `/v1/embeddings` 端点在协程里**同步**调用 `model.encode()`，
推理期间整个事件循环不可用 —— 于是所有请求（包括健康检查）一起排队，
从外部看就是「彻底挂了」。积压耗尽后它自己恢复了。

---

## 一、初始误判

C4 容量测试需要用 Qwen 嵌入服务把 500 / 2000 个分块向量化，客户端超时设的是 30s。
结果全部 `ReadTimeout`。随后做能力探测，连「1 条 10 字」都 90s 超时。

当时的结论是「我把服务压挂了」。**这个结论是错的。**

---

## 二、排查过程（九步）

排查的核心原则是**逐层剥离**：先把「进程死没死」和「功能对不对」分开，
再把「框架层」和「推理层」分开。每一步只回答一个问题。

### 第 1 步：TCP 层 —— 进程还在吗？

```python
socket.connect(("192.168.86.132", 8000))
```

| 服务 | 端口 | 结果 |
|---|---|---|
| Qwen-Embedding | 8000 | **可达** |
| Redis | 6379 | 可达 |
| Milvus | 19530 | 可达 |
| PostgreSQL | 5432 | 可达 |
| **MinIO** | 9000 | **ConnectionRefused** ← 附带发现 |

**结论**：端口能握手 ⇒ 进程活着、监听正常。**不是宕机。**

> 这一步排除了「进程崩溃 / 容器挂掉 / 机器断电」三类最常见原因。

### 第 2 步：HTTP 框架层 —— 哪些端点还活着？

| 端点 | 结果 |
|---|---|
| `GET /health` | **200**（485ms） |
| `GET /v1/models` | **200**（363ms） |
| `GET /docs` | **200**（411ms） |
| `GET /` | 404（正常，未定义根路由） |
| **`POST /v1/embeddings`** | **ReadTimeout（15s）** |

**结论**：FastAPI/uvicorn 框架层完全健康，路由注册正常。**只有推理这一条路径有问题。**
问题被精确定位到「模型推理」而不是「服务整体」。

> 注意响应时间 363–485ms 偏慢（正常应是毫秒级），说明事件循环当时已经被挤压。

### 第 3 步：超长超时重测 —— 是「不响应」还是「很慢」？

把客户端超时拉到 300s 重打：

```
1 条 x 2 字     200   7.27s   dim=1024
1 条 x 40 字    200   1.42s   dim=1024
3 条 x 40 字    200   1.80s   dim=1024
```

**结论**：服务已经**自行恢复**。所以此前不是「死锁」，是**被压到长时间无响应后自己缓过来**。
第一条 7.27s 明显是冷启动/回热，后续 1.4–1.8s 属正常。

### 第 4 步：容器状态 —— 是被重启了，还是自己好的？

```
Up 3 hours (healthy)
RestartCount=0
StartedAt=2026-09-14T03:22:29Z
CPU 0.14%   MEM 1.714GiB / 3.773GiB
```

**结论（关键）**：`RestartCount=0` ⇒ **从未重启**，是**自愈**。

> ⚠️ **更正（当日补测）**：本步最初还依据「CPU 只有 0.14%」推断「不是在忙着算，是卡住不动」。
> **这条推理是错的**——那个采样点是在积压已经排空之后取的，它描述的**不是阻塞期间的状态**。
> 精细重测（见第 7 步之二）显示：阻塞期间容器 CPU 实际为 **110–121%**（2 核上限 200%），
> 是**有实实在在的算力在跑**的。正确表述见下。

> 不过这一步推翻「压挂」叙事的**主要依据是 `RestartCount=0`**，
> 这一条不受上述更正影响：压挂会表现为 OOMKilled 或重启，两者都没有。
> 真实机制是「阻塞」而非「过载崩溃」（CPU 确实在忙，但并没有被榨干）。

### 第 5 步：读日志 —— 请求到底怎么样了？

- 容器生命周期内**只记录了 52 条** embeddings 请求
- 存在**客户端早已超时、服务端却回 200** 的记录

**结论**：存在「客户端放弃、服务端继续算」的错位。
uvicorn 只在响应发出后才记访问日志，所以**大量请求从未走到"完成"这一步**。
这些"幽灵请求"正是把服务拖住的原因。

> 顺带发现一个独立问题：**VM 时钟曾发生跳变**。
> 同一条日志流里，旧行时间戳是 `2026-06-14T15:44`，新行是 `2026-09-14T06:42`，
> 而 VM 与容器当前时间都是正确的。这是虚拟机随宿主休眠后时钟漂移的典型症状
> （宿主是笔记本）。⇒ **跳变点之前的日志时间戳不可用于取证**，
> 也会影响 Prometheus / Grafana 的日志关联与任何依赖时钟的逻辑（JWT、TLS）。

### 第 6 步：读服务端源码 —— 找到根因

```python
@app.post("/v1/embeddings", response_model=EmbeddingResponse)
async def embeddings(req: EmbeddingRequest):      # ← async def
    ...
    vecs = model.encode(                          # ← 同步阻塞调用
        texts, show_progress_bar=False, normalize_embeddings=True,
    )
```

**这就是根因**：声明成 `async def` 的端点里直接调用同步的 `model.encode()`。
协程跑在事件循环上，这个调用会把**整个事件循环**占住 ——
不只是当前请求，是**所有**请求，连 `/health` 都拿不到 CPU 时间。

同时确认了三个环境事实：

```
DEVICE=cpu          MODEL_NAME=Qwen/Qwen3-Embedding-0.6B
MAX_BATCH_SIZE=32   MAX_LENGTH=8192
```

宿主：**2 vCPU（i5-13500H）/ 3GB 内存 / 无 GPU / 无 CPU 与内存限额**。

### 第 7 步：容器内探针 —— 验证阻塞假说

外部探针还可能有「网络/连接队列」的替代解释。所以改从**容器内部**打 `/health`，
彻底排除网络变量：

| 状态 | 容器内 `/health` |
|---|---|
| 空闲（基线，连续 3 次） | `200` / 2.5ms、1.2ms、2.4ms |
| 重负载开始后第 1 次 | **`000` / 5.0s（超时）** |
| 重负载开始后第 2 次 | **`000` / 5.0s（超时）** |
| 第 3 次起 | 200 / 约 4ms |

**结论**：阻塞假说成立。推理期间事件循环**确实不可用**；
请求接近尾声时才恢复（尾部只是 tokenizer 统计与 JSON 序列化，不占多久）。

> 这一步是整份报告里最关键的一步：它把「很可能」变成了「确定」。

### 第 7 步之二：阻塞期间 CPU 到底占了多少？（区分「阻塞」与「耗尽」）

「事件循环被阻塞」**不等于**「CPU 资源耗尽」——这是两件必须分清的事。
前者是**并发能力**问题，后者是**资源容量**问题。它们的修复手段完全不同。

在 2 核机器上 `docker stats` 的 CPU 上限是 **200%**。若真是 CPU 被榨干，
数字应贴近 100~200%。实测（16 条 × 255 字，请求总耗时 41.4s）：

```
容器内 nproc = 2    torch.get_num_threads() = 2

采样点      容器 CPU%     /health（容器内探测）
1           114.10%       000  3.00s   ← 超时
2           112.08%       000  3.00s   ← 超时
3           121.33%       000  3.00s   ← 超时
4           109.65%       200  0.005s  ← 恢复
5~10        0.11~0.27%    200  ~0.002s
```

**两条结论：**

1. **CPU 没有被耗尽。** 峰值 110–121% ⇒ 约 1.2 个核在忙，**约 0.8 个核闲着**。
   没有超订、没有排队争抢。CPU 是「忙」，不是「枯竭」。
2. **能否响应与 CPU 忙不忙无关。** 第 4 个采样点上 CPU 仍是 **109.65%**，
   而 `/health` 已经能 5ms 返回 —— 同一时刻，CPU 一样忙，响应能力却恢复了。
   说明瓶颈是**事件循环这个单一线程是否可用**，不是 CPU 还剩多少。

**为什么会误判成「CPU 耗尽」：** 表面症状确实像（请求排队、全部超时）。
但排队发生在**线程调度层**而不是 CPU 调度层：整个进程里只有事件循环那一个线程
被允许处理请求，它被占住了，后面的请求就连「被调度」的机会都没有 —— 哪怕 CPU 有空闲核。

> 因此本次故障是两个**独立**问题叠加，必须分开修：
> ① 并发能力（事件循环阻塞）→ 改代码；
> ② 资源容量（0.4 条/秒）→ 换硬件/换模型。
> **只修 ①，吞吐仍是 0.4 条/秒；只修 ②，高负载下服务照样整体假死。**

### 第 8 步：容量标定 —— 它到底能扛多少？

用 255 字的真实分块（SmartChunker 的实际产出长度）测：

| 批量 | 耗时 | 条/秒 | 单条耗时 |
|---|---|---|---|
| 1 | 13.12s | 0.08 | 13118ms ← 冷启动 |
| 4 | 8.12s | 0.49 | 2031ms |
| 8 | 19.46s | 0.41 | 2432ms |
| 16 | 43.41s | 0.37 | 2713ms |
| 32 | 79.91s | 0.40 | 2497ms |

**结论**：吞吐稳定在 **约 0.4 条/秒**，**加大批量几乎没有收益**（1→32 批量的单位吞吐不变）。
它是**算力受限**（0.6B 参数 / 2 核 CPU），不是调度受限。

⇒ **每小时约 1,440 条；10,000 个分块需要约 7 小时。**

并发行为：2 个并发请求，自身耗时 26.11s / 39.77s，墙钟 40.35s —— 存在部分重叠但不翻倍，
**并发不能提升吞吐，只会拉长排队**。

### 第 9 步：还原事故链

把上面的证据串起来，完整的因果链是：

1. C4 客户端按 `BATCH=20~100` 灌库，客户端超时 **30s**；
2. 而一条 20 条的分块请求服务端需要 **约 50s**，100 条需要 **约 250s**；
3. **所有请求必然超时** → 客户端放弃并（脚本里）继续/重试；
4. **服务端不因客户端断开而取消** `async def` 任务，继续算完；
5. 于是又叠加下一批 → 积压；
6. 事件循环被第一条长请求占住 → 后续请求连读都读不进来 → 全部超时；
7. 从外部看：**「服务彻底挂了」**；
8. 积压逐条消化完 → 服务**自行恢复**。

**这是一次「客户端凭错误假设施加了不可能完成的工作量」导致的假死，不是服务故障。**

## 三、根因（分三层，缺一不可）

| 层 | 问题 | 严重度 |
|---|---|---|
| **直接原因** | `/v1/embeddings` 是 `async def` 却同步调用 `model.encode()`，推理期间**阻塞整个事件循环** | 🔴 高 |
| **放大因素** | 客户端 30s 超时 vs 服务端 50–250s 实际耗时；**服务端不取消已断开的请求** | 🟠 中 |
| **容量现实** | 0.6B 模型跑在 2 核 CPU 上，吞吐 **0.4 条/秒**，批量无效 | 🟠 中 |

两点必须澄清：

- 第 1 条是**并发能力**问题，第 3 条是**资源容量**问题，**性质不同、修法不同**。
  「阻塞事件循环」**不等于**「CPU 耗尽」——实测阻塞期间 CPU 仅 110–121%（2 核上限 200%），
  尚有约 0.8 个核空闲。详见第 7 步之二。
- **即使修好事件循环阻塞，第 3 条依然成立** —— 10,000 分块仍要 7 小时。
  反之，只提升算力而不改代码，高负载下服务照样会整体假死。两者要分开治理。

### 补充澄清：为什么「1 条 10 字」也会超时 90 秒？

这不是因为那条小请求**自己**算得慢 —— 它单独跑只要 1.4s。
真正的原因是**排队**：

1. 事件循环被一个长请求占住时，**新连接根本读不进来**。
   它们停在内核的 TCP 接收队列里，连成为「任务」的机会都没有。
2. 长请求算完后，循环才从队列里取出下一个请求 —— 又是一个需要数十秒的长请求。
3. 于是那条 10 字的小请求要等**它前面所有请求逐一算完**才轮到自己。
   90 秒的等待 = 排队前面请求的累计计算时间，不是它自己的开销。

> 换句话说：**阻塞负责制造队列，队列负责制造超时。**
> 两者一起才凑成「连 10 个字都不理人」这种看着像宕机的现象。
> 修复事件循环阻塞后，队列依然存在（吞吐没变），但请求会**老实地排队并返回**，
> 而不是连读都读不进来 —— 超时变成干净的超时，可用性也回来了。

## 五、解决方案

### 5.1 立刻可做（0 风险）

**a) 不需要重启服务。** 想清场的话：
```bash
ssh www@192.168.86.132 "echo '123456' | sudo -S docker restart qwen-embeddings-2.0-small"
```

**b) 修客户端：灌库前先量吞吐，超时按批量算。**
`scripts/capacity_test.py` 里的 30s 硬超时是本次事故的直接扳机。
正确做法是 `timeout = 30 + 2.5 * batch_size`，或干脆用 `--synthetic` 量延迟。

### 5.2 真正的修复（服务端一行改动）

把阻塞调用挪出事件循环 —— 这是投入产出比最高的一处：

```python
import asyncio
from starlette.concurrency import run_in_threadpool

# CPU 只有 2 核，真并发只会上下文抖动；用信号量串行化。
# 但信号量只限制「同时进入推理的数量」，不再阻塞事件循环。
_decode_sem = asyncio.Semaphore(1)


@app.post("/v1/embeddings", response_model=EmbeddingResponse)
async def embeddings(req: EmbeddingRequest):
    if model is None:
        raise HTTPException(status_code=503, detail="Model not loaded yet")

    texts = _normalise_input(req.input)

    # 原实现：vecs = model.encode(...)   ← 阻塞事件循环
    async with _decode_sem:
        vecs = await run_in_threadpool(
            model.encode,
            texts,
            batch_size=MAX_BATCH_SIZE,
            show_progress_bar=False,
            normalize_embeddings=True,
        )

    token_ids = model.tokenizer(texts)["input_ids"]      # 顺带省掉一次重复分词
    total_tokens = sum(len(ids) for ids in token_ids)
    ...
```

顺带两点：
- 原实现里 `model.encode()` 之后**又单独跑了一遍 `model.tokenizer.encode(t)`** 来统计 token 数，
  等于把分词做了两遍。上面顺手合并掉了。
- 为什么这样就不阻塞了：`await run_in_threadpool(...)` 让事件循环线程在发起调用后
  **立刻返回到 `run_forever()`**，encode 跑到另一个线程上执行。
  事件循环因此能继续处理 `/health` 与其他连接。
  （顺带说明一个常见误解：torch 在张量运算期间确实会释放 GIL，
  但**释放 GIL 并不能把事件循环挪到别的线程上** —— 循环是某个特定线程，
  而它当时正卡在 `encode()` 里。真正起作用的是「换了执行线程」，不是 GIL。）

改完后：**吞吐不变（仍是 0.4 条/秒），但服务不再"假死"** ——
请求会老老实实排队并返回，超时是干净的超时，健康检查也拿得到响应。
实测对比：同一份 16 条负载下，修前阻塞期间 `/health` 连续超时，
修后事件循环线程全程可服务其他请求（CPU 占用两者相同，均为约 1.2 核）。

> **一个容易想到但无效的方案：「给 encode 内部加 await」。**
> `await` 本身不是魔法 —— 它只在「被 await 的对象会交还控制权」时才挂起。
> 给一个纯 CPU 的计算函数里插入 `await asyncio.sleep(0)`，**确实**能让事件循环
> 重新变得可响应（因为协程在让出点交还了控制权），**但吞吐一点都不会变** ——
> 计算仍然跑在事件循环线程上，只是把「一次长阻塞」切成了「很多次短阻塞」。
> 真正要解决的是**换线程执行**，不是「加让出点」。
> 三种写法的实测对比见 `scripts/async_blocking_demo.py` 与第六节。

### 5.3 容量问题（要选一条路）

0.4 条/秒意味着 10,000 分块 = 约 7 小时。可选：

| 方案 | 效果 | 代价 |
|---|---|---|
| 接受现状，灌库异步化（后台任务 + 进度查询） | 不改硬件，链路可用 | 首次入库要等数小时 |
| 换更小的嵌入模型 | 可能快 2–4 倍 | 需重建 collection，检索质量待评估 |
| **用本机 RTX 4050 跑嵌入** | 快 1–2 个数量级 | 要装 CUDA 版 torch；当前 torch 是 CPU 版 |
| 换商业嵌入 API | 最快，无运维 | 花钱 + 数据出境 |

> 项目现状：torch 是 `2.14.0+cpu`，**用户的 4050 完全没被用上**。
> 这是当前最大的一块闲置算力。

### 5.4 监控补位（本次暴露的真实盲区）

**没有任何指标或告警能发现这次故障。** 原因：

1. 容器健康检查是 `curl -f http://localhost:8000/health`（30s 间隔）——
   **只探一个空壳端点**，永远不碰真实推理路径。
   功能上完全不可用时，它照样报 `healthy`。**这个健康检查是无效的。**
2. 嵌入服务不暴露 `/metrics`，Prometheus 无数据可采。
3. 现有规则里唯一沾边的是 `RagRetrievalSlowP95 > 1s`，
   但要求 `for: 5m` **且有流量** —— 灌库期间正是没有查询流量的时段。

建议（任选，成本递增）：
- **最小改动**：把健康检查从 `/health` 改成一次真实的小推理
  （如 `curl -X POST .../v1/embeddings -d '{"input":["ping"]}'`），
  并对该端点加长 `--start-period`。
- **补一条**：加 Blackbox Exporter 探 `/v1/embeddings`，配 `probe_duration_seconds` 告警。
- **根治**：在嵌入服务里加 `prometheus_client`，导出

## 六、复现方式

```bash
# 1. 事件循环阻塞验证 + 批量吞吐标定 + 并发行为（约 8 分钟）
.venv\Scripts\python.exe -u scripts/embedding_service_probe.py

# 2. 只跑阻塞验证（约 1 分钟）
.venv\Scripts\python.exe -u scripts/embedding_service_probe.py --health-only

# 3. 原理演示：同一个 CPU 计算，三种写法下事件循环的可用性（约 10 秒，纯本地）
#    不需要 VM，也不需要网络
.venv\Scripts\python.exe -u scripts/async_blocking_demo.py
```

脚本 1、2 会**真实施加负载**并在此期间探测 `/health`，因此会短暂降低该服务的可用性。
请在没有人使用它的时候跑。脚本 3 是纯本地演示，随时可跑。

脚本 3 的输出形态（三者的**计算量相同**）：

```
写法                                      墙钟耗时        最长冻结
A. async def + 直接调用                    2.05s        2047ms   <-- 事件循环被冻住
C. 函数里插入 await 让出                      2.00s         107ms
B. await asyncio.to_thread(...)        2.08s          62ms
```

三者墙钟几乎相同（纯 Python 循环受 GIL 限制，换线程并不会更快），
但事件循环的**可用性差了 30 倍** —— 这直接说明：
这一层的修复目标是**恢复并发能力**，而不是提升吞吐。
